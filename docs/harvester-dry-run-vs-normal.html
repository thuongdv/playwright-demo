Repository Context & Architecture

The page-map harvester is an autonomous discovery engine built on Playwright and Chromium. It inspects live web applications, walks the DOM, identifies accessible interactive elements and assertion landmarks, and compiles them into version-controlled JSON page maps.

Command & Target Setup
  • package.json maps harvest to npx tsx .agents/harvester/run.ts
  • Reads target list from .agents/harvester/targets.ts
  • Default App URL: https://automationexercise.com
  • Override App URL via environment variable: AUT_URL
Target Snapshot Profile
  • pageKey: SignupLoginPage
  • route: /login
  • role: unauthenticated
  • variant: default (root: body)
  • Output: .agents/page-map/SignupLoginPage.unauthenticated.default.json
22 Captured Live Elements
  • Headings: Login to your account
  • Links: Home, Products, Cart
  • Textboxes: Email Address, Password
  • Buttons: Login, Signup

Schema Validation & The ariaDigest

The harvester computes a deterministic SHA-256 fingerprint (ariaDigest) representing the discovered structure. When evaluating changes against the existing JSON snapshot, the comparison verifies:

  • Interactive & Semantic properties: role, accessibleName, testId, locator, and fallbackLocators.
  • State & Context: element count, visible, enabled, and requiresScoping.
  • Structural sanitization: Inaccessible controls (e.g. buttons lacking both an accessible name and a test ID) are recorded in the notes array and excluded from primary locators.
  • Strict Zod Schema: Every newly built page-map object is strictly parsed and schema-validated prior to output.
CLI Options & Flexibility 
# Harvest only a single targeted page
npm run harvest -- --only SignupLoginPage

# Harvest using a custom configuration file
npm run harvest -- --config .agents/harvester/custom-targets.ts

# Override the base application URL
AUT_URL="https://staging.automationexercise.com" npm run harvest -- --dry-run

Execution Modes: Dry Run vs Normal Run

Dry Run Mode
Observation Only

Command:

Terminal 
npm run harvest -- --dry-run

Exact Execution Steps:

  1. Launches headless Chromium via Playwright.
  2. Navigates to the configured application URL and /login route.
  3. Harvests all interactive nodes and semantic landmarks on the live page.
  4. Builds and schema-validates a new in-memory PageMap object.
  5. Computes the fresh SHA-256 ariaDigest.
  6. Loads the existing JSON file and compares the digests and structures.
  7. Reports whether the page map is unchanged or changed in stdout.
  8. Does NOT write or modify the JSON file on disk.

Sample Terminal Output:

2026-08-19 10:35:03 [info] [harvester/run.ts]: .agents/page-map/SignupLoginPage.unauthenticated.default.json: 22 elements, unchanged (dry-run, not written) 2026-08-19 10:35:03 [info] [harvester/run.ts]: Harvest complete — no changes.

22 relevant accessibility and interactive elements were successfully identified on the live /login DOM.

unchanged

The newly calculated ariaDigest exactly matches the stored digest in the committed JSON snapshot.

(dry-run, not written)

Normal Run Mode
Observe & Synchronize

Command:

Terminal 
npm run harvest

Execution & Output Scenarios:

Performs the exact same browser navigation, harvesting, schema validation, and digest comparison as dry-run, but writes the generated JSON to disk.

Case 1: Page is Unchanged

• Output log reports unchanged.
• The JSON file is re-written deterministically with Prettier formatting.
• Historical metadata (capturedAt, appBuild, firstSeenBuild) is preserved.
• Result: Zero git diff; workspace remains completely clean.

Case 2: Page Has Changed

• Output log reports changed or UPDATED.
• The updated JSON file is written containing newly discovered elements, locators, and an updated ariaDigest.
• Final log reports:
Harvest complete — one or more page maps changed.

Case 3: Element Disappears or Attributes Mutate

• Digest discrepancy triggers change detection.
• Normal Run: Automatically synchronizes the page map file to match the new live state.
• Dry Run: Flags and reports the discrepancy in stdout while leaving the repository snapshot untouched.

What the Harvester Does Not Do

To avoid common misconceptions among QA and test automation engineers, the harvester has clearly bounded responsibilities:

Non-Goals & Boundary Constraints
  • It does NOT run business-flow tests: It maps page elements; it does not execute end-to-end user journeys.
  • It does NOT submit forms: It will never fill out or submit login, registration, or checkout forms.
  • It does NOT verify login success: It captures the unauthenticated or authenticated initial page state as configured, without validating credential success.
  • It does NOT test locators through user workflows: It ensures locators can be formed and resolved on the page, but does not simulate full click/type sequences.
  • It does NOT treat the existing JSON as assertions: The JSON file is a versioned snapshot, not a test suite of assertions.
  • It does NOT use an LLM for element extraction: All element filtering, role mapping, and locators are computed deterministically using standard DOM/ARIA rules.
  • It does NOT modify files during a dry run: Disk writes are completely disabled when --dry-run is active.

Important Distinction

Core Architectural Principle

The harvester does not simply open the existing JSON file and check every locator one by one. It first inspects the live /login page, creates a new page map, and then compares the new page structure with the stored page map using ariaDigest. The stored JSON is the previous versioned snapshot, not the primary source of discovery.
